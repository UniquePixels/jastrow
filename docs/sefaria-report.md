# Jastrow Lexicon — Data Issues Report (for Sefaria)

**Who.** The jastrow.app project (Brian L.), which rebuilds Marcus
Jastrow's dictionary from Sefaria's export of it: `lexicon_entry`,
`parent_lexicon: "Jastrow Dictionary"`, snapshot 2026-07-04, 32,512
entries.

**What.** Errors in that export that are Sefaria's own: OCR misreadings
(a wrong letter, a lost or wrong vowel point, a numeral read as a
letter) and Sefaria's parsing and linking (a sense cut in the wrong
place, a numeral moved off its headword, a cross-reference aimed at the
wrong homograph). Some of these may come from the digitization that
preceded Sefaria's import; they are in the served data either way.

**What is never sent.** Our own corrections of print's errors
(anything we store with an annotation of print's reading), Jastrow's
own conventions (the implied `1)`, the implied homograph I, print's
lettering and doubled numbers), and the structures of our own data
model. They are the right repairs for jastrow.app, not errors in
Sefaria's copy of the book.

**The bar** (the maintainer, 2026-10-16): "this is my reputation here,
so whatever is sent to them must be solid and verified. No slop, no
garbage, no ambiguous etc. Just solid, errors from OCR or Sefaria
parsing." It is built into the appendix generator as hard filters
(`docs/decisions.md`, row `10-16 upstream report`).

## How to read this report

There are four documents. This one is hand-written; the next three are
generated by `bun data:sefaria` (`admin/pipeline/sefaria.ts`) from the
reviewed patch records, the raw source and the submission log, and are
regenerated whenever any of them changes.

| document | holds | for Sefaria? |
|---|---|---|
| this report | one section per class: what is wrong, how to find it, the fix | yes |
| [`reports/sefaria-appendix.csv`](reports/sefaria-appendix.csv) | one row per verified instance | yes |
| [`reports/sefaria-appendix.md`](reports/sefaria-appendix.md) | the appendix's counts by class, what is new, the review list's counts by reason | no |
| [`reports/sefaria-review.csv`](reports/sefaria-review.csv) | every reviewed patch the filters held back, with the reason | no: it is our work list |

**An appendix row** is one reviewed patch that passed all four filters:

1. **Sefaria's own error.** No annotation (so not our correction of
   print), no ruling 10-13 case 2, 3 or 4, no recorded deviation from
   print, no repair that leaves part of print's text unrestored, and
   not one of the classes or ops that are Jastrow's convention or our
   own structure (the list is in `admin/pipeline/report/sefaria-evidence.ts`).
2. **Evidence.** The patch's rationale names a print read: an hOCR
   line, a scan leaf, or the maintainer's read of the printed page with
   its date. A cross-reference retarget may instead rest on Jastrow's
   own words: the cite reads `X N`, and exactly one entry of X's family
   carries `N` in Sefaria's own data (or once a print-read row of this
   appendix restores the numeral Sefaria dropped, which the evidence
   column names). Every scan the rationale links must show a page the
   entry is on.
3. **Traceable to Sefaria's string.** Our patches apply after our own
   transform rules, so the row is located in Sefaria's raw record
   instead: the changed text, with its context, must occur exactly once
   in the raw field. A row whose text our rules had already changed, or
   which occurs twice, is held back.
4. **Still there.** The check runs against the source as fetched, so a
   re-fetch in which Sefaria has fixed a row drops it.

**The columns.** `rid` is the entry's id in Sefaria's record and our
key; `sefaria_oid` is its Mongo `_id`; `sefaria_headword` its headword
as Sefaria stores it. `field` is the path in Sefaria's record
(`content.senses[2].definition`, `headword`, `alt_headwords[0]`).
`sefaria_text` is Sefaria's current string, verbatim (a substring of
that field, with enough context to occur once); `corrected_text` is the
same span as print has it. `evidence` names the print read or the text
proof; `scan` links the page image (Internet Archive's scan of the
1903 edition, University of Toronto copy); `patch_id` is our record;
`first_seen` is the date of the review that found it; `submitted_batch`
names the batch that sent it, empty for a row not yet sent.

**Notation in the text cells.** `‖` marks a boundary between two sense
objects: the text after it is the next sense, its `number` first. A
`field` such as `content.senses[0–1]` names two adjacent senses, read
as the first definition, `‖`, the second number and the second
definition. `(absent)` is a field the record does not carry; `(empty)`
is a field left empty. `alt_headwords` without an index is the whole
array, as JSON.

**The submission log** is [`sefaria-submissions.jsonl`](sefaria-submissions.jsonl),
kept by hand: one line per batch sent, `{"batch", "date", "channel",
"patch_ids" or "classes", "response"}` (`response` is `""` until one
comes). The generator marks every row a batch names with that batch:
by its patch id, or by its class when the row was first seen on or
before the batch's date (a class sent once does not cover rows found
later). A row with an empty `submitted_batch` is new since the last
submission. The log is empty: nothing has been sent yet. **483 rows are
ready to send** (generator, 2026-10-27, PR #NNN).

**Each class below says what it is** for the submission:

- `rows: appendix class X`: its verified instances are appendix rows.
- `rule-level: see pattern`: our import repairs it by a rule over the
  whole corpus; the section gives the detection, there are no rows.
- `informational`: worth knowing, and nothing here to send as rows.
- `withdrawn`: not to be sent.

Each count says which count it is: appendix rows and review-list
patches are the generator's output (2026-10-16, or the date the count
gives); an import count is a
transform rule's composed count in `reports/import-blessing.md`; a
snapshot count is measured over `data/source/`, the 2026-07-04
snapshot the original counts were taken from (re-measured 2026-10-16).

## 2. Phantom sense boundaries (36 entries)

**Status:** rows: appendix class `verse-paren-false-sense-split` (15
rows: a citation's own verse number taken as a sense marker, each read
on the scan) and `reviewed-join` (20 rows: the 36 cross-reference-form
entries listed below, review doc 01, 2026-08-05). Their records named
no print read until PR #192 quoted the hOCR line into 32 of them (review
ledger L71); the other 4 took the maintainer's scan read of 2026-10-25
(PR #193), each `N)` closing a cross-reference's parenthesis. Of the 36,
20 are rows, 12 are held back as not traceable to Sefaria's string and
4 as a join into the entry's own head.
**Count:** 35 appendix rows; 16 `reviewed-join` in the review list
(generator, 2026-10-25); 2 more of the verse-paren class are held back
because the text is not traceable to Sefaria's string. A01002's two
(P000388, P000389) joined the appendix on 2026-10-22, once their
rationale named its own leaf (review ledger L70).

The sense segmentation treats `N)` as a sense-number marker. In 36
entries the matched `N)` is actually the tail of a parenthesized
cross-reference or a citation's verse number, so the entry is split
into a phantom "sense 2" (etc.) with no sense 1, and the preceding
text is left with an unclosed `(`.

**Example — `A00913` (אוּרְתָּא).** The printed text is one flow:
`אוּרְתָּא f. (v. אוֹר 2) evening, night. Pes. 2ᵃ…` — "(see אוֹר,
sense 2)". Current data:

```json
"senses": [
  { "definition": " (v. <a …>אוֹר</a>" },
  { "number": "2)", "definition": "<i>evening, night</i>. <a …>Pes. 2ᵃ</a>; …" }
]
```

**Fix:** merge the two objects — concatenate
`definition₀ + number + definition₁` and drop the phantom boundary:

```json
"senses": [
  { "definition": " (v. <a …>אוֹר</a> 2) <i>evening, night</i>. <a …>Pes. 2ᵃ</a>; …" }
]
```

**Detection:** any sense whose `number` matches `^\d+\)$` with a
value ≠ `1)` and whose preceding text (previous sense's definition,
prepending `morphology`/`language_code`/`language_reference` when the
previous sense is the first) contains more `(` than `)`.

**Affected (cross-reference form, all 35):** A00913, A01662, A03104,
A03277, B00534, B00656, B00991, H00709, H00871, I00137, I00149,
I00753, J00301, K01188, L00346, N00327, N00740, N01381, O00821,
O01360, O01397, P00286, P00539, P00805, P00859, P01088, P01094,
P01436, Q02145, R00096, S01040, U00261, U00398, U01674, V00166.
**Citation form (1):** C00244 (sense boundary at `…I Chr. IV, 4)`,
a verse number).

## 4. Etymology parenthesis split mid-phrase across fields

**Status:** rule-level: see pattern. jastrow.app folds the two
language fields back into the gloss head (`admin/pipeline/body/rejoin.ts`),
so it repairs the split structurally rather than entry by entry; the
catalogue's `unmatched-opening-paren` (452 entries) and
`common-gender-inexpressible` (228) are its detectors. Two reviewed
patches restore a `)` Sefaria dropped (M00712, Q01198), but each also
dropped a Hebrew word our hOCR cannot read, so the repair is partial and
both are held back (`partial: print not fully restored`). **Count:**
5,842 entries carry a language field (snapshot count, re-measured
2026-10-16).

`language_code` / `language_reference` hold crude segments of the
entry's opening parenthesis. In many entries the split lands
mid-phrase, and in some the parenthesis never closes inside the
language fields at all — the closing `)` sits at the start of the
first sense's `definition`. Gender markers are sometimes caught in
the wrong field too.

**Example — `K00664` (כִּכָּר):**

```json
"language_reference": " c. (b. h.; = <span dir=\"rtl\">כרכר</span>",
"content": { "senses": [ { "definition": ", v. <a …>כִּרְכֵּר</a>) [<i>circle</i>,] …" } ] }
```

Note the gender marker `c.` inside `language_reference`, and the
parenthesis opening there but closing in `definition`.
**Example — `A00014` (אָב II):** `language_code` is `"(b. h.;"` and
the first definition begins `" , const. …"` — an orphaned comma.

**Fix:** re-derive the two language fields by splitting at phrase
boundaries, or store the parenthesis whole. Systemic: 5,842 entries
carry the split; the mid-phrase cases are detectable by unbalanced
parens across the field boundary.

## 5. Malformed anchors — href swallows following markup (2 entries)

**Status:** rule-level: see pattern (`unterminated-href-swallows-closing-tag`,
`admin/pipeline/transform/rules/malformed-href.ts`). **Count:** 2 entries,
D00478 and J00597 (import count: the rule fires on exactly these two).
J00603, listed here before, carries no unterminated `href` in this
snapshot.

**Entries:** `D00478`, `J00597`

An `<a>` open tag's `href` value is never quote-terminated, so the
stored attribute contains following markup, and in J00597 a
neighboring valid anchor is consumed into it.

**Example — `J00597`:**

```html
<a dir="rtl" class="refLink" href="/Jastrow,_דִּלְדֵּל.1</a><a class="refLink" href="/Bava_Metzia.38b" …>
```

**Fix:** close the first anchor properly:

```html
<a dir="rtl" class="refLink" href="/Jastrow,_דִּלְדֵּל.1" data-ref="Jastrow, דִּלְדֵּל 1">…</a> <a class="refLink" href="/Bava_Metzia.38b" …>
```

```html
<a dir="rtl" class="refLink" href="/Jastrow,_*איבּוּס.1" data-ref="Jastrow, *איבּוּס 1">כפר א׳</a>
```

**Fix:** the link should target the K'far Imra-related entry (or be
unlinked). Found by eye during manual review; a systematic sweep
would need anchor-text ↔ target-headword comparison, so there may be
more of these. The same sense also opens with `*  pr. n. pl.` (star
followed by a double space) — the star likely belongs elsewhere in
the printed text (displaced during digitization).

## 14. Form sections flattened into the preceding sense

**Status:** informational. A data-model gap, not a transcription
error. **Count:** as below (snapshot counts, unchanged).

In the printed dictionary, a related grammatical form — a noun's
plural (`—Pl. <form> …`), or (found during a later print pass,
2026-07-14) a verb's passive participle (`—Part. pass. <form> …`),
feminine (`—Fem. <form> …`), or denominative (`—Denom. <form> …`) —
opens a separate lemma-level section after the preceding senses,
sometimes with its own numbered sense set restarting at `1)`. The
data model has no structure for this: every such section is
flattened into the tail of the preceding sense's `definition`
string. **All entries carrying one of these markers are affected**
(5,484 with `Pl.` in this snapshot, plus smaller counts for the
other three); in the 13 entries where the section carries its own
numbering — `Pl.` 5 (A01047, B01292, C00062, D00194, E00789),
`Part. pass.` 6 (A02260, A03348, C00869, C00964, C01139, H01022),
`Fem.` 1 (G00644), `Denom.` 1 (I00311) — the flattening is visibly
damaging because two independent numbering sequences end up
interleaved in one senses array. (D00194 carries both a `Fem.`
section and a numbered `Pl.` section; the numbering belongs to the
nearer `Pl.` marker, not the earlier `Fem.` one.)

**Example — `C00062` (גְּבוּרָה).** The end of sense `—3)`'s
definition currently reads:

```
…from the mouth of the Lord.—Pl. גְּבוּרוֹת 1) manifestations of
Divine power, wonders. … —2) mighty deeds…
```

The `1)` and `2)` here are not sub-points of sense 3 — they are the
plural lemma's own senses. A faithful structure would be, in outline:

```text
senses: 1) strength…  2) …  3) might of God…
plural (גְּבוּרוֹת): 1) manifestations of Divine power…  2) mighty deeds…
```

**Detection (numbered form):** tag-stripped definition matching one
of the four markers followed within ~120 characters by a bare `1)` —
but with paren-balance tracking from the marker forward: a naive
match yields 38 candidates across the four markers (`Pl.` 25,
`Part. pass.` 10, `Fem.` 2, `Denom.` 1), of which 25 are false
positives where the `1)` is a chapter/paragraph number closing a
parenthetical citation (`Lam. R. introd. (R. Joḥ. 1)` style), or —
for one of the two `Fem.` candidates (D00194) — a run that genuinely
belongs to a different, later marker section. The genuine 13 are
listed above; each was verified by hand.

## 15. `refs` field is missing ~33k citations that appear inline

**Status:** informational. jastrow.app drops `refs` and derives its
reference index from the inline citations (ruling B7). **Count:** as
below (snapshot counts, unchanged).

The `refs` array tracks which texts an entry cites, but it is far
from complete against the entry's own body: **13,841 entries carry
at least one inline citation (a `refLink` anchor with a `data-ref`)
that does not appear in their `refs` — 32,899 citations in total.**
Even matching loosely (is the cited *book* present in `refs` at
all?), 13,259 entries / 29,640 citations are missing.

**Example — `A00014` (אָב II):** `refs` lists 34 items, yet the
body's inline citations of `Mishnah Kelim 1:1`, `Mishnah Bava Kamma
1:1`, `Mishnah Chagigah 2:2`, and `Leviticus 20:27` are absent.
**Example — `A00013` (אָב I):** `refs` has 2 items; inline
`Mishnah Rosh Hashanah 1:3` and `Mishnah Taanit 4:6` are missing.

**Detection:** per entry, collect every `data-ref` from `refLink`
anchors across all sense definitions plus `language_code`/
`language_reference`, drop the `Jastrow, …` internal ones, and diff
against the `refs` array. (The reverse direction is near-perfect:
99.97% of existing `refs` items correspond to an inline citation —
so `refs` behaves like an incomplete derivation of the body text.)

The full 32,899-row list (rid → missing refs) is machine-generated
and available on request — happy to attach it when filing.

## 16. Sense lists that start at 2 (informational — matches print)

**Status:** withdrawn. Jastrow's own convention, transcribed faithfully;
jastrow.app's inserted `1)` is our correction, recorded with an
annotation, and is not sent. **Count:** 118 reviewed patches carry it
(review list, `convention or our structure`).

This one is not a transcription error. We raise it because it affects
anyone who reads the sense numbers as data.

When sense 1 is only a cross-reference right after the grammatical
label, Jastrow's print leaves out the `1)` and the next sense opens
`—2)`. Sefaria transcribes this faithfully, so a consumer sees a
sequence that starts at 2.

**Example — `B01321` (בַּרְקַאי II):**

```json
{ "definition": ", v. <a … data-ref=\"Jastrow, בּוֹרְקַי II 1\">בּוֹרְקַי II</a>." },
{ "number": "—2)", "definition": " כְּפַר ב׳ <i>K’far Barkai</i>, in Palestine; …" }
```

**Size, each confirmed in our review:** 3 entries where it shows in
the sense list (`B01321`, `C01169`, `U01787`), and 41 more where the
`—2)` run sits inside the first sense's text, because the unnumbered
first sense was never split (`D00072` among them). A further 21
candidates of the in-text shape have not been reviewed yet, so treat
44 as a floor, not a total.

**What we did:** jastrow.app inserts the `1)` itself and records each
insertion as a deviation from print. Whether to do the same is your
call; we only want you to know the shape exists.

**Detection:** a `senses` list whose first numbered sense is `2)`
(or `—2)`), or an unnumbered sense whose text contains a `—2)` with
no `1)` before it.

## 17. Combining marks stored out of canonical (NFC) order (201 strings, 175 entries)

**Status:** rule-level: see pattern (ruling HW-nfc-write: jastrow.app
normalizes to NFC when it writes). **Count:** 201 strings in 175
entries (snapshot count, re-measured 2026-10-16).

201 strings are not in Unicode Normalization Form C: the marks that
stack on a letter are stored in a non-canonical order, and a few
Latin/Greek letters are stored as a base plus a separate diacritic
rather than the precomposed character. The text is canonically
equivalent either way and renders identically, so nothing is visibly
wrong — but any byte-exact comparison (search, de-duplication, a
lookup keyed on a headword) silently fails to match.

**Breakdown**

| Field | Strings |
|---|---|
| `content.senses` | 169 |
| `plural_form` | 12 |
| `refs` | 8 |
| `alt_headwords` | 6 |
| `language_reference` | 6 |

165 of the 201 are Hebrew mark-order only; the other 36 compose a
Latin or Greek diacritic (`Ḥ`, `ḳ`, `ḫ`, `ṇ`, `Ἀ`, `ά`).

**Example — `A00018`, an `alt_headwords` item** ('אַכָּה'): the dagesh
is stored before the qamats, where NFC puts the vowel first.

```
stored:  U+05D0 U+05B7 U+05DB U+05BC U+05B8 U+05D4
NFC:     U+05D0 U+05B7 U+05DB U+05B8 U+05BC U+05D4
```

**Fix:** normalize every string field to NFC on export. The operation
is lossless and verifiable — `NFD(before) == NFD(after)` holds for all
201 — and no Hebrew letter+point sequence composes into a presentation
form, because those are on Unicode's composition-exclusion list.

**Detection:** for every string in the record, compare it with its own
NFC form; any inequality is an instance.

## 18. ר read for ד inside quoted text (`ורע` for `ודע`)

**Status:** informational. One confirmed instance, still stored as
Sefaria has it in our data; no reviewed patch yet, so no row. The hOCR
cannot supply one: it reads the quotation as Latin glyphs, `to refute.
Ab.II, 14 '31 3il25ni25 na Wi that you may know` (1528a · leaf 851),
and does not tell ר from ד (review ledger L71, 2026-10-22).
**Count:** 1 (snapshot count).

**Entries:** `U00311` (confirmed); the class is not yet counted
corpus-wide.

Distinct from §1, which is ר/ד's neighbour ך/ד in a HEADWORD. This is
the ר/ד pair inside a definition's quoted Hebrew, where neither the
headword nor the `prev_hw`/`next_hw` chain can witness the error.

U00311's definition quotes Avot 2:14 as `ורע מה`. Avot 2:14 reads
`וְדַע מַה`, and Jastrow's own gloss for the quoted word is "know" —
`ודע`, not `ורע`. The two letters differ by the length of one stroke
and are a standard OCR confusion in this typeface, so the class is
very unlikely to be one entry; it is listed here with the one
confirmed instance rather than an estimate.

**Fix:**

```diff
- "definition": "… ורע מה …"
+ "definition": "… ודע מה …"
```

**Detection:** no reliable purely-textual predicate — ר and ד are both
real letters and both spellings are well-formed Hebrew. The instance
above was found by reading a quotation against its cited source, which
is how we expect the rest of the class to surface.

a bare Roman numeral; neither is a proof alone (print leaves some first
homographs unnumbered), so each row here was read on the scan.
